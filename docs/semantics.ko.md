# 쿼리 의미 규칙

[English](semantics.md) | 한국어 | [简体中文](semantics.zh-CN.md)

> 이 문서는 [semantics.md](semantics.md)(커밋 ffa5953)의 번역이다. 내용이 다르면 영어 원문을 따른다.

이 문서는 sparql-v12n이 SPARQL 쿼리를 SQL로 변환하는 방법과 쿼리 결과를 결정하는 규칙을 설명한다. 다루는 항목은 컬럼 이름, IRI, 리터럴(literal), 상수, 조인, 중복, `OPTIONAL`, `UNION`, `FILTER`, 정렬이다. 전체 개요와 지원 기능 표는 [README](../README.ko.md)에 있다.

## 컬럼 이름

`rr:column`, 템플릿, 조인 조건에 쓰는 컬럼 이름은 SQL 식별자다(R2RML §5).
컬럼 이름은 다음 두 방식 중 하나로 해석한다.

- `"\"Name\""`처럼 큰따옴표로 감싼 식별자는 대소문자를 바꾸지 않고 작성한
  그대로 해석한다.
- 일반 이름은 PostgreSQL이 따옴표 없는 이름을 해석하는 방식으로 해석한다. 이
  방식에서는 이름이 소문자로 바뀐다.

예를 들어 `rr:column "StudentId"`는 `SELECT ... AS StudentId`가 만드는 컬럼인
`studentid`를 읽는다. 같은 이유로 `rr:column "Name"`은 `"Name"`으로 생성한
컬럼과 일치하지 않는다.

일반 이름을 사용하는 쿼리를 실행하기 전에, 엔진은 PostgreSQL이 그 이름을
해석하도록 probe 문을 준비한다. 그런 다음 해석된 이름을 생성된 SQL에서
큰따옴표로 감싼다. 소문자, 숫자, `_`로만 이루어진 이름에는 probe 문이 필요하지
않다.

## 상대 IRI

`rr:termType rr:IRI`인 컬럼이나 템플릿은 `Carlos`, `person/7` 같은 상대 IRI를
생성할 수 있다. R2RML은 상대 IRI를 프로세서에 지정된 base IRI를 기준으로
해석한다(R2RML §4, §11.2).

이 해석은 RFC 3986 방식의 해석이 아니라 단순한 문자열 연결이다. 예를 들어
base가 `http://data.example.com/`이면 다음과 같다.

- `Carlos`는 `<http://data.example.com/Carlos>`가 된다.
- `../x`는 `<http://data.example.com/../x>`가 된다.

템플릿 값은 먼저 퍼센트 인코딩한다. 예를 들어 `Bob/Charles`는
`Bob%2FCharles`가 된다.

base IRI의 기본값은 없다. base IRI는 `base_iri`, `--base-iri`,
`V12N_BASE_IRI`로 설정한다. 설정하지 않으면 상대 IRI는 R2RML 데이터 오류가
되며, 오류 메시지에 이 설정의 이름이 표시된다. 따라서 엔진이 데이터의 IRI를
임의로 만들어 내는 일은 없다. base IRI는 데이터가 속한 네임스페이스로 설정한다.
이 값은 절대 IRI여야 한다.

`http:`나 `urn:` 같은 스킴으로 시작하는 문자열은 절대 IRI로 간주한다.
프래그먼트가 있어도 상대 IRI로 간주하지 않는다.

스킴이 있지만 유효한 IRI가 아닌 문자열은 데이터 오류다. R2RML 규칙대로라면
이런 문자열은 먼저 앞에 base IRI를 붙여 본다. 두 규칙은 포트가 숫자가 아닌
`http://host:port/` 같은 값에서만 다르다. 엔진의 규칙을 사용하면 아래의 SQL
비교에도 결과와 같은 규칙을 적용할 수 있다.

- `{name}`이나 `person/{id}`처럼 텍스트에서 스킴이 생길 수 없는 템플릿은
  매핑을 읽을 때 앞에 base IRI를 붙인다. 그러면
  `<http://data.example.com/person/7>` 같은 상수는 이전과 같이 컬럼에서 일치
  여부를 검사하며(`id = $1`), 이때 컬럼의 인덱스를 사용한다.
- 컬럼 값은 상대 형태일 수도 있고 절대 형태일 수도 있다. 따라서 상수는 두 형태
  모두와 일치한다. `$1`, `$2`가 각각 `http://data.example.com/a`와 `a`인
  `iri IN ($1, $2)`가 그 예다. 이 조건도 컬럼의 인덱스를 사용한다.
- 이런 컬럼을 조인할 때는 생성된 IRI를 SQL에서 비교한다. 값에 따라 스킴이
  달라지는 `{scheme}:{rest}` 같은 템플릿을 조인할 때도 마찬가지다. 비교식은
  `CASE WHEN iri ~ '^scheme:' THEN iri ELSE $base || iri END` 형태다. 이
  비교에는 컬럼의 인덱스를 사용할 수 없다.
- 중복은 컬럼 값을 기준으로 제거한다. 따라서 `a`와
  `http://data.example.com/a`처럼 상대 값과 그 값을 해석한 절대 IRI는 여전히
  두 번 센다. 이 때문에 base IRI가 설정되어 있으면 이런 컬럼에 대한
  `SELECT DISTINCT`는 미지원으로 거부한다.

참고로 Ontop 5.5.0은 절대 IRI로 시작하지 않는 모든 템플릿 앞에 W3C 테스트
케이스의 base IRI인 `http://example.com/base/`를 붙인다. Ontop에는 이 base를
바꾸는 설정이 없다. 또한 Ontop은 컬럼에서 생성된 상대 IRI를 처리하지 못한다.

## 컬럼 값의 문자열 표기

엔진은 문자열이 아닌 모든 값의 문자열 표기(lexical form)를
정규 표기(canonical form)로 출력한다. 정규 표기는 XML Schema 1.1 Part 2가
정의하는 형태이며, R2RML이 참조하는 버전도 이 버전이다. 이 규칙은 리터럴과
템플릿 값 모두에 적용한다.

- `numeric` 12.50과 3.00은 `"12.5"^^xsd:decimal`과 `"3"^^xsd:decimal`이
  된다. 정수 값인 decimal에는 소수점이 없다.
- `float8` 30은 `"3.0E1"^^xsd:double`이 된다.
- `boolean`은 `true`/`false`가 된다.
- `bytea`는 대문자 16진수가 된다.

따라서 결과는 컬럼에 선언된 스케일(scale)에 영향을 받지 않는다.

Ontop은 정규 표기 대신 PostgreSQL의 텍스트 출력(`12.50`,
`"30"^^xsd:double`)을 사용한다. 차등 테스트는 이 차이를 알려진 차이로
기록한다(이슈 #25).

SQL `=`가 서로 다르다고 판단하는 두 값이 하나의 term일 수 있다. PostgreSQL은
`time '24:00:00'`과 `'00:00:00'`을 구분한다. XSD 1.1은 둘을 같은 값에
대응시키며, 이 값을 `00:00:00`으로 표기한다. 두 값 모두
`"00:00:00"^^xsd:time`이 되므로 다음과 같이 동작한다.

- 상수 `"00:00:00"^^xsd:time`은 두 값 모두와 일치한다.
- 상수 `"24:00:00"^^xsd:time`은 어떤 값과도 일치하지 않는다.
- 조인, `DISTINCT`, `UNION`, `ORDER BY`는 두 값을 하나의 값으로
  처리한다(`col + interval '0'`).

`time` 컬럼의 유일 키는 쿼리에 중복이 없음을 증명하는 데 사용하지 않는다.
Ontop은 `24:00:00`을 그대로 출력한다(이슈 #37).

SQL `=`가 같다고 판단하는 두 값이 서로 다른 term일 수도 있다. 다음이 그런
경우다.

- `real`과 `double precision` 컬럼에서 `-0`과 `0`은 각각 `"-0.0E0"`과
  `"0.0E0"`이 된다.
- `char(n)` 값은 채움 공백을 유지하지만, `char(n)`에 대한 `=`는 이 공백을
  무시한다. 예를 들어 `'a'::char(3)`은 `"a  "`가 된다.

엔진은 상수, 조인, `sameTerm`, 그리고 `DISTINCT`와 `UNION`의 중복 제거에서
이런 컬럼을 term으로 비교한다. 이때 값의 텍스트(0인 경우)나 길이(`char(n)`인
경우)도 함께 비교한다. 이 비교는 `=` 비교에 추가하는 방식이므로, 컬럼의
인덱스로 여전히 행을 찾을 수 있다.

## 쿼리 안의 상수

트리플 패턴(triple pattern) 안의 상수는 SPARQL이 요구하는 대로 RDF term으로
일치 여부를 판단한다. 문자열 표기와 데이터타입(datatype)이 모두 같아야 한다.
컬럼 값은 R2RML 자연 매핑(natural mapping)을 거쳐 비교된다. 예를 들어
`integer` 컬럼은 정규 표기의 `xsd:integer`를, `numeric` 컬럼은 정규 표기의
`xsd:decimal`을 만들며, 다른 타입도 같은 방식이다.

다음 표는 7을 담은 integer 컬럼과 일치하는 상수를 보여 준다.

| 상수 | 일치 | 이유 |
|---|---|---|
| `7`, `<…/customer/7>` | 예 | |
| `"7"`, `"7"^^xsd:decimal`, `7.0` | 아니오 | 데이터타입이 다르다 |
| `"07"^^xsd:integer`, `<…/customer/007>`, `<…/customer/+7>` | 아니오 | 상수가 매핑이 만드는 정규 표기가 아니다 |
| `99999999999`, `<…/customer/99999999999>` | 아니오 | 값이 컬럼의 범위를 벗어나므로 이 값을 가진 행이 없다 |

상수는 SQL 텍스트에 넣지 않고 항상 바인드 파라미터로 PostgreSQL에 전달한다.

바인딩(binding)하기 전에 엔진은 각 상수를 PostgreSQL이 컬럼에서 추론한
파라미터 타입과 대조한다. 대조는 다음 단계로 진행한다.

1. 엔진은 상수를 그 타입의 값으로 읽는다.
2. 결과 term을 만드는 코드와 같은 코드로 값을 다시 문자열로 변환한다.
3. round trip 결과가 원래 값과 동일할 때만 상수를 전달한다. 타입이 허용하면
   상수를 바이너리 형식으로 전달한다.

일치할 수 없는 상수가 있으면 그 상수가 속한 `UNION` branch를 비운다.
PostgreSQL이 해석할 수 없는 입력 때문에 실패하도록 두지 않고 이렇게 처리한다.
`OPTIONAL` 부분 안에서는 그 부분만 일치하지 않고, 그 왼쪽의 해(solution)는
유지된다. 남은 branch가 없으면 쿼리를 데이터베이스에 보내지 않는다.

비교는 컬럼 자체의 타입으로 수행하므로 컬럼의 인덱스를 사용한다.

`interval`처럼 자연 데이터타입이 없는 컬럼 타입도 있다. 이런 타입은 결과에
컬럼을 텍스트로 캐스트한 값이 담긴다. 상수는 같은 텍스트와
비교한다(`col::text = $1`). 이 비교에는 컬럼의 인덱스를 사용할 수 없다.

## 리터럴

리터럴은 어디서나 RDF 1.1 term으로 비교한다. 트리플 패턴, 조인, `sameTerm`,
RDFterm-equal을 뜻하는 `FILTER` 안의 `=`, `DISTINCT`, 결과가 모두 해당한다.

- 언어 태그(language tag)는 대소문자를 구분하지 않고 비교한다(RDF 1.1
  Concepts §3.3). 따라서 엔진은 언어 태그를 소문자로 유지한다. 예를 들어
  `rr:language "EN-us"`는 `"chat"@en-us`가 되고, 상수 `"chat"@EN-US`는 이
  term과 일치한다. 태그의 대소문자만 다른 두 term map은 하나의 term을 만든다.
  유효한 BCP 47 언어 태그가 아닌 태그는 매핑 오류다(R2RML §7.5).
  `rr:datatype rdf:langString`도 매핑 오류다. `rdf:langString`은 언어 태그가
  있는 문자열에만 쓰는 데이터타입이기 때문이다.
- 단순 리터럴(simple literal)은 `xsd:string` 리터럴이다. `"x"`,
  `"x"^^xsd:string`, text 컬럼, `rr:datatype xsd:string`인 컬럼, 리터럴
  템플릿은 모두 같은 term을 만든다. 결과에서는 이 term을 데이터타입 없이
  표기한다. `DATATYPE`은 `xsd:string`을 반환한다.
- 어떤 term map도 만들지 않는 데이터타입은 트리플 패턴에서 일치하는 경우가
  없다. 예를 들어 integer 컬럼은 `xsd:integer` term을 만들므로, 트리플
  패턴에서 `"5"^^xsd:int`와 `"5"^^xsd:decimal`은 어떤 값과도 일치하지 않는다.
  사용자 정의 데이터타입도 트리플 패턴에서 어떤 값과도 일치하지 않는다.
  `FILTER`에서는 숫자를 값으로 비교하며, `xsd:float`와 파생 정수 타입은
  거부한다(`FILTER` 참고).
- `char(n)` 값은 RDF term에서도 뒤쪽 채움 공백을 유지한다. SQL 표준과 W3C
  RDB2RDF 기대 출력도 공백을 유지한다(D018: `"Venus          "`). 채움 공백이
  없는 값이 필요하면 `varchar`나 `text`, 또는 `rtrim()`을 사용하는 R2RML 뷰를
  사용한다.

데이터타입이 다른 값 사이의 비교는 `FILTER`에서 처리한다(아래 참고). integer
컬럼에 대한 `FILTER(?amount = 7.0)`이 그 예다.

## 여러 컬럼이 공유하는 변수

두 번 나타나는 변수는 조인이 된다. 조인에서도 SQL 값이 아니라 RDF term을
비교한다.

이런 쿼리를 실행하기 전에 엔진은 관련 컬럼의 타입을 PostgreSQL에 조회한다.
이를 위해 probe 문을 준비한다. 그런 다음 엔진은 다음과 같이 처리한다.

- 같은 종류의 컬럼(정수, 텍스트, 날짜, ...)은 `=`로 비교하므로 인덱스를
  사용한다.
- 그 밖의 컬럼 쌍은 SQL에서 계산한 자연 문자열 표기로
  비교한다(`int_col::text = text_col::text`). 이때 먼저 자연 데이터타입을
  확인한다. 예를 들어 7을 담은 `integer` 컬럼은 text 컬럼에
  `rr:datatype xsd:integer`가 지정된 경우에만 그 컬럼과 조인된다. `numeric`
  7.0과는 조인되지 않는다. `numeric` 값의 정규 표기는
  `trim_scale(col)::text`(PostgreSQL 13 이상)로 계산한다. 이 표기가 엔진
  자체의 변환 결과와 같은지는 테스트로 확인한다.
- 템플릿이나 IRI 컬럼을 문자열로만 비교할 수 있으면, 템플릿 값을 IRI와 같은
  방식으로 퍼센트 인코딩한다(R2RML IRI-safe version).
- SQL에서 문자열 표기를 계산할 수 없으면 쿼리를 미지원으로 거부한다(종료 코드
  1, HTTP 501). text 컬럼과 비교하는 `float8` 또는 날짜/시간 템플릿 값이 그
  예다. 엔진은 PostgreSQL에서 실패하거나 잘못된 행을 반환하는 대신 이런
  쿼리를 거부한다.

## 타입이 다른 컬럼에 걸친 변수

한 패턴의 term map들은 SQL 타입이 서로 다른 컬럼에서 변수 값을 읽을 수 있다.
예를 들어 한 triples map에서는 `integer` 컬럼에서, 다른 triples map에서는
`text` 컬럼에서 같은 변수의 값을 읽을 수 있다.

`UNION`은 결과 컬럼마다 하나의 타입을 요구한다. 따라서 여러 term map에 걸친
쿼리에서는 엔진이 선택된 컬럼의 타입도 PostgreSQL에 조회한다. 그런 다음
엔진은 다음과 같이 처리한다.

- 값을 바꾸지 않고 타입을 합칠 수 있으면 결과 컬럼 하나를 유지한다. `int4`와
  `int8`, `text`와 `varchar`가 그 예다.
- 자연 데이터타입의 리터럴은 데이터타입마다 별도의 결과 컬럼으로 나눈다. 각
  branch는 자기 컬럼을 채우고 나머지 컬럼은 `NULL`로 둔다. 그 결과 정수 120은
  `"120"^^xsd:integer`로, 텍스트 `'120'`은 `"120"`으로 유지된다.
- 두 타입이 같은 term을 만들 수 있으면, 조인과 마찬가지로 SQL에서 계산한 자연
  문자열 표기를 선택한다. 그러면 두 term map에서 생성된 같은 트리플(triple)도
  한 번으로 센다. 다음 term이 여기에 해당한다.
  - 템플릿 값(`integer` 키와 `text` 키에 대한 `item/{id}`는 둘 다 `item/1`이
    된다)
  - IRI 컬럼
  - `rr:datatype`이나 언어 태그가 있는 리터럴
  - `text`와 `uuid` 컬럼의 일반 리터럴(plain literal)
- 이 표기를 SQL에서 계산할 수 없으면 쿼리를 미지원으로 거부한다. `float8`,
  `double precision`과 함께 쓰인 `real`, 날짜/시간, `char(n)`이 여기에
  해당한다.

## 중복 트리플

RDF 그래프는 트리플의 집합(set)이다. 따라서 트리플은 그 트리플을 만드는 행이
몇 개든 한 번으로 센다. 다음 경우에는 여러 행이 같은 트리플을 만들 수 있다.

- 키가 없는 테이블의 중복 행
- 행을 반복하는 R2RML 뷰
- 같은 트리플을 만드는 두 term map

기본 그래프 패턴(basic graph pattern)은 모든 변수의 서로 다른 바인딩마다 해를
하나씩 가진다. `SELECT`는 그 뒤에 투영한다. 따라서
`SELECT ?city WHERE { ?p ex:city ?city }`는 여전히 사람마다 도시를 한 번씩
반환한다.

생성된 SQL은 `DISTINCT`로, 또는 term map 사이에서는 `UNION`으로 중복을
제거한다. 중복 제거는 패턴의 모든 변수에 해당하는 컬럼을 기준으로 수행한다.
그 변수 중 선택되지 않은 변수가 있으면 하위 쿼리에서 중복을 제거한다.

일부 쿼리는 (`UNION`의 어느 한쪽에서) term map 조합 하나로 테이블(뷰가 아닌)을
읽는다. 이런 쿼리를 실행하기 전에 엔진은 카탈로그에서 해당 테이블의 유일 키를
읽는다. 모든 테이블이 해가 고정하는 컬럼 중에 키를 가지고 있으면, 두 행이
같은 해를 만들 수 없다. 이때 SQL은 `DISTINCT` 없이 모든 행을 유지한다.

그렇지 않으면 PostgreSQL이 중복을 제거해야 한다. 이때 행 전체에 대한 해시나
정렬 비용이 든다. 인덱스가 행을 정렬된 순서로 전달하지 않는 한, PostgreSQL은
첫 행을 반환하기 전에 모든 행을 읽기도 한다.

`v12n explain`은 데이터베이스 없이 실행되므로 항상 `DISTINCT`를 보여 준다.

중복은 컬럼 값으로 비교한다. 따라서 템플릿이 같은 문자열로 만드는 서로 다른
두 값은 여전히 두 번 센다. 예를 들어 템플릿 `{a}-{b}`는 값 `x-`, `y`와 값
`x`, `-y`를 같은 문자열로 만든다.

선택되지 않은 변수는 그 컬럼의 타입과 텍스트 출력으로 비교한다. 따라서 다음
경우에는 같은 term도 두 번 셀 수 있다.

- SQL이 문자열 표기를 계산할 수 없는, 타입이 다른 컬럼
- `varchar`와 `text`처럼 타입을 합칠 수 있는 컬럼
- `numeric` 1.0과 1.00처럼 타입은 같지만 텍스트 출력이 다른 값

## OPTIONAL

`OPTIONAL`은 SPARQL algebra의 LeftJoin을 따른다. 왼쪽의 모든 해는 유지된다.
optional 부분에 호환되는 해가 있으면 왼쪽 해를 그 해 각각으로 확장한다. SQL은
optional 부분마다 `LEFT JOIN`을 하나씩 사용한다.

- 한 부분의 테이블은 서로 조인한다. 테이블이 여러 개이면 괄호로 묶는다. `ON`
  절에는 부분 자체의 조건과 왼쪽과의 연결 조건을 둔다.
- 중첩된 `OPTIONAL`은 바깥 `LEFT JOIN` 안의 `LEFT JOIN`이다. `OPTIONAL` 뒤에
  작성한 패턴은 그 `OPTIONAL` 다음에 조인한다.
- 공유 변수는 조인과 마찬가지로 RDF term으로 비교한다. 따라서 타입이 있는
  컬럼과 템플릿 분해도 같은 방식으로 처리한다. 양쪽이 모두 단순 컬럼이면
  인덱스를 사용한다.
- 바인딩되지 않은 변수는 SQL에서 `NULL`이며 JSON 바인딩에서는 제외된다.
- 공유 변수가 한쪽에서 바인딩되지 않을 수 있다. 앞선 `OPTIONAL`만 그 변수를
  바인딩하거나, 부분 안에 중첩된 `OPTIONAL`만 그 변수를 바인딩하는 경우다.
  이런 변수는 어떤 값과도 호환된다. 이때 조건은 `(left IS NULL OR left = right)`
  이며, 이 조건에는 컬럼의 인덱스를 사용할 수 없다.
- algebra의 평가 방식대로 각 부분을 먼저 독립적으로 변환한다. 따라서 중첩된
  부분을 바깥 왼쪽과 연결하는 조건은 바깥 부분의 `ON` 절에서 검사한다. 중첩된
  부분 안에서는 이 조건을 검사하지 않는다.
- `OPTIONAL` 부분에서만 바인딩되는 변수는 해당하는 각 부분에서 컬럼을 받는다.
  그 값은 그 행에서 처음으로 바인딩된 값이다.
- optional 부분의 상수 term에는 플래그 컬럼이 함께 생성된다. 이 플래그는 그
  부분이 일치했는지를 나타낸다.
- 다른 기본 그래프 패턴과 마찬가지로 중복 트리플은 각 부분 안에서 한 번으로
  센다.

optional 부분은 둘 이상의 방식으로 일치할 수 있다. 둘 이상의 triples map
조합이 그 부분과 일치할 수 있거나, 그 안의 `UNION`에서 둘 이상의 쪽이 일치할
수 있는 경우다. 이때 그 부분은 이 선택지들의 합집합이며, algebra에서 다음
항등식이 성립한다.

LeftJoin(L, R1 ∪ R2)는 Join(L, R1) ∪ Join(L, R2) ∪ Diff(L, R1 ∪ R2)다.

SQL branch도 이에 따라 나뉜다.

- 선택지마다 branch 하나. 이 branch는 그 선택지의 `LEFT JOIN`과, 그 부분이
  일치했다는 `WHERE` 조건을 가진다. PostgreSQL은 이 branch를 inner join으로
  바꾼다.
- 모든 선택지의 `LEFT JOIN`과, 어느 선택지도 일치하지 않았다는 `WHERE` 조건을
  가진 branch 하나. 이 branch는 anti-join이다. 이 branch는 아무것으로도
  확장되지 않는 왼쪽 해를 유지한다.

각 부분은 자기 `ON` 절을 유지한다. 따라서 부분이 하나일 때와 마찬가지로,
부분의 일치 여부는 호환성과 `OPTIONAL` 안의 `FILTER`가 결정한다. 바깥 부분
안에서는 이렇게 나뉜 branch가 바깥 부분의 선택지가 된다. 빈 쪽이 있는
`UNION`에서는 빈 쪽을 거쳐 모든 왼쪽 해가 변경 없이 확장된다.

다음은 아직 지원하지 않으며 미지원으로 거부한다.

- 여러 `OPTIONAL` 부분에서만 바인딩되는 변수에 대한 `SELECT DISTINCT`
- 빈 쪽이 있는 `UNION`을 감싼 `OPTIONAL` 안의 `FILTER`

## UNION

`{ A } UNION { B }`의 해는 양쪽 해를 모은 bag이다. 양쪽에서 모두 생성되는 해는
두 번 센다. `SELECT DISTINCT`에서는 한 번 센다. 한쪽에서만 바인딩되는 변수는
다른 쪽의 해에서 바인딩되지 않는다.

- 조인, `FILTER`, `OPTIONAL`은 왼쪽에 있는 합집합에 대해 분배된다. **arm**은
  모든 `UNION`에서 한쪽씩 고른 조합이다. 이 분배가 성립하므로 엔진은 각 arm을
  따로 unfold하고 arm들을 `UNION ALL`로 합친다.
- 각 arm은 다른 패턴과 같은 방식으로 변환한다. 중복 트리플은 arm 안에서 한
  번으로 센다. arm은 `DISTINCT`나 term map 사이의 `UNION`을 사용하고, 키로
  중복이 없음이 증명되면 둘 다 사용하지 않는다. 키는 arm마다 따로 검사한다.
  arm끼리는 서로 비교하지 않는다.
- 각 arm은 term map 조합마다 SQL branch 하나를 가진다. 모든 arm의 branch를
  합한 수는 64개로 제한되며, 이는 한 패턴의 branch 수 제한과 같다.
- 한쪽 안의 `FILTER`는 그쪽의 해에만 적용된다. 합집합을 감싼 그룹의
  `FILTER`는 양쪽 해 모두에 적용된다. 이 해에서 다른 쪽의 변수는 바인딩되지
  않은 상태다.
- `OPTIONAL` 안의 `UNION`은 left join에 대해 분배되지 않는다. 이 `UNION`의
  양쪽은 optional 부분의 선택지다(`OPTIONAL` 참고). 각 쪽의 해는 자기 arm에
  남는다.

변수는 형태가 다른 term map에서 값을 받을 수 있다. 형태는 합집합의 양쪽
사이에서, 또는 term map 사이에서 다를 수 있다.

- 한쪽은 템플릿이고 다른 쪽은 컬럼이나 다른 템플릿인 경우
- 상수, IRI, 리터럴
- 데이터타입이나 언어 태그가 다른 리터럴

결과는 각 값을 그 행을 생성한 branch의 term map으로 다시 구성한다. 경우는 두
가지다.

- 결코 같아질 수 없는 형태의 term은 별도의 결과 컬럼을 사용한다. 각 branch는
  자기 컬럼을 채운다. 이 컬럼들에 대한 중복 제거는 정확하게 유지된다. 이런
  형태는 다음과 같다.
  - `http://example.org/customer/{id}`와 `http://example.org/wholesale/{code}`
    같은 두 템플릿. 고정 텍스트가 다르거나, 한쪽 템플릿에 다른 쪽 값에서는
    IRI-safe 인코딩이 항상 이스케이프하는 텍스트가 있는 경우다
  - IRI와 리터럴
  - 서로 다른 두 상수
  - 두 언어 태그
- 같은 term을 만들 수 있는 형태들은 한 arm 안에서나 `SELECT DISTINCT`에서
  중복을 비교할 때 결과 컬럼 하나를 공유한다. 이 컬럼은 term의 문자열을
  담는다. SQL은 조인과 마찬가지로 이 문자열을 계산한다(IRI-safe 템플릿, base
  IRI를 기준으로 해석한 IRI, 자연 문자열 표기). 그래서 템플릿에서 생성된
  트리플과 IRI 컬럼에서 생성된 같은 트리플은 한 번으로 센다. 이런 컬럼에는
  인덱스를 사용할 수 없고, 문자열은 모든 행에서 계산된다. 이 경우는 다음 두
  상황에서 미지원으로 거부한다.
  - 조인과 마찬가지로 SQL이 문자열 표기를 계산할 수 없는 경우
  - 형태 중 하나가 자연 데이터타입의 컬럼인 리터럴. 이 컬럼의 데이터타입은
    SQL 타입에 따라 정해진다

## FILTER

`FILTER`는 오류를 포함해 SPARQL의 평가 규칙을 따른다. 오류는 참도 거짓도
아니다. `error || true`는 참, `error && false`는 거짓이고, `!error`는 여전히
오류다.

SQL에서는 오류를 `NULL`로 나타낸다. SQL의 `AND`, `OR`, `NOT`도 `NULL`을 같은
방식으로 처리한다. `WHERE`는 필터가 참인 행만 남긴다. SPARQL에서 오류인
비교는 SQL에서 `false`가 아니라 항상 `NULL`이다. 따라서 `FILTER(!(?x = 5))`는
`?x`가 바인딩되지 않았거나 문자열인 행을 제외한다.

필터의 적용 범위는 다음과 같다.

- 그룹 안의 `FILTER`는 그룹 안에서 작성한 위치와 관계없이 그룹 전체에
  적용된다. 이 필터는 그 그룹의 변수만 참조한다. 예를 들어
  `{ ?s ex:name ?n { ?s ex:qty ?q FILTER(?n = "x") } }`에서 필터는 오류다.
  중첩된 그룹 안에서는 `?n`이 바인딩되지 않기 때문이다.
- `OPTIONAL` 안의 `FILTER`는 그 부분의 `LEFT JOIN`의 `ON` 절에 들어간다. 이
  필터는 부분의 일치 여부를 결정한다. 왼쪽의 어떤 행을 유지할지는 결정하지
  않는다. 이 필터는 왼쪽의 변수를 참조할 수 있다. 필터가 오류이면 SQL의
  `LEFT JOIN`과 마찬가지로 그 부분은 일치하지 않는다.
- `OPTIONAL` 뒤의 `FILTER`는 `WHERE`에 들어가 행을 제외한다.
- 바인딩되지 않은 변수는 `BOUND`를 제외한 모든 함수에서 오류다.
- `OPTIONAL` 부분에서만 바인딩되는 변수는 일치한 부분에서
  읽는다(`CASE WHEN part matched THEN ... END`).

비교는 SPARQL 연산자 매핑(operator mapping)을 따른다.

| 피연산자 | `=`, `!=`, `<`, `<=`, `>`, `>=` |
|---|---|
| 숫자(`xsd:integer`, `xsd:decimal`, `xsd:double`) | 값으로 비교하며 XPath 타입 승격을 적용한다. `7.0`은 정수 7과 같고, `-0`은 `0`과 같으며, NaN은 어떤 값과도 같지 않다. |
| 문자열(단순 리터럴, `xsd:string`) | 코드 포인트 순(`COLLATE "C"`, UTF-8 데이터베이스가 필요하다). |
| `xsd:boolean` | `false` < `true`. |
| `xsd:dateTime` | 두 값 모두 시간대가 있거나 모두 없으면 시점으로 비교한다. 시간대가 있는 값과 없는 값의 비교는 암묵적 시간대에 따라 결과가 달라지므로 거부한다. |
| IRI, 빈 노드(blank node), 그 밖의 타입의 리터럴 | RDF term으로서(RDFterm-equal) `=`와 `!=`만 사용할 수 있다. `<`와 그 밖의 연산자는 오류다. 서로 다른 두 리터럴은 오류다. |

컬럼과 비교하는 상수는 컬럼의 타입으로 변환해도 결과가 같으면 컬럼의 타입으로
변환한다. 그러면 컬럼의 인덱스를 사용할 수 있다. 예를 들어 `?qty > 5`는
`qty > $1::int8`이 되고, `?qty = 7.0`은 `qty = $1::int8`이 된다.

그렇지 않으면 컬럼을 XPath 승격 규칙에 따른 타입으로 캐스트하며, 이 비교에는
컬럼의 인덱스를 사용할 수 없다. 예를 들어 `?qty < 5.5`는 integer 컬럼을
`numeric`으로, `?qty < 5.5e0`은 `float8`로 캐스트한다.

`sameTerm`, `BOUND`, `isIRI`, `isBlank`, `isLiteral`, `STR`, `LANG`,
`DATATYPE`을 지원한다. boolean 값이 필요한 위치의 term은 그 term의 유효 불리언
값(effective boolean value)을 뜻한다. 빈 문자열과 0은 거짓이다.

컬럼에 대한 `STR`과 `DATATYPE`은 조인과 마찬가지로 SQL에서 그 컬럼의 문자열
표기나 자연 데이터타입을 알 수 있을 때 동작한다. `date`와 `timestamp`의
무한대 값은 일반 리터럴이므로 그 `DATATYPE`은 `xsd:string`이다.

`REGEX`는 XPath 정규식을 일치 결과가 같은 PostgreSQL 패턴으로 변환한다. 이
패턴은 `COLLATE "C"`에서 `~` 연산자로 적용한다.

| XPath | PostgreSQL 패턴 |
|---|---|
| `.`(`s` 없이) | 줄바꿈과 캐리지 리턴을 제외한 모든 문자, `[^\u000A\u000D]`. |
| `^`, `$` | 문자열의 시작과 끝. PostgreSQL의 기본 동작과 같다. |
| `m`을 지정한 `^`, `$` | 줄 경계. 단 마지막 줄바꿈 뒤는 제외한다(XPath 3.1). lookaround를 사용한다. |
| `i` | 각 문자를 대소문자 변형(`lower-case`나 `upper-case`가 같은 문자)으로 확장한다. 따라서 데이터베이스 로캘과 관계없이 `i`는 `ı`와도 일치하고, `k`는 켈빈 기호와도 일치한다. |
| `\s` | 정확히 공백, 탭, 줄바꿈, 캐리지 리턴. |
| `x` | 문자 클래스 밖의 공백 문자를 제거한다. |
| 그 밖의 문자 | ASCII 영문자나 숫자가 아니면 `\uXXXX` 이스케이프로 변환한다. |

다음은 미지원으로 거부한다.

- `\d`, `\w`, `\i`, `\c`, `\p{..}`와 그 여집합. 이들은 PostgreSQL에서는
  로캘을 통해서만 사용할 수 있는 Unicode 클래스다
- 역참조
- 문자 클래스 빼기
- 255를 넘는 반복 횟수
- 문자 클래스 안의 `\S`
- `q` 플래그
- 상수가 아닌 패턴이나 플래그

잘못된 패턴이나 플래그는 XPath와 마찬가지로 오류다.

다음은 SPARQL을 확장한 엔진과 다른 결과를 반환하는 대신 미지원으로 거부한다.

- 위 표에 없는 데이터타입에서 같은 데이터타입의 두 리터럴을 정렬하거나
  비교하는 것. `xsd:date`가 그 예다
- 부정 밖에서 쓰는 `=`를 제외하고, 언어 태그가 있는 두 리터럴을 정렬하거나
  비교하는 것
- 다음 중 하나에 대한 비교
  - `real` 컬럼
  - `rr:datatype`이 컬럼의 자연 데이터타입이 아닌 숫자, boolean, dateTime
    데이터타입인 컬럼의 값
  - `xsd:float`와 파생 정수 타입
  - 1년부터 9999년 범위를 벗어나거나 마이크로초보다 정밀한 dateTime 상수
- 그 밖의 함수, 산술, `IN`, `EXISTS`, 그리고 term(변수, 상수, 이들에 대한
  `STR`, `LANG`, `DATATYPE`)이 아닌 식을 피연산자로 쓰는 것
- 인코딩이 UTF-8이 아닌 데이터베이스에서의 문자열 정렬과 `REGEX`

## ORDER BY, LIMIT, OFFSET

해 수정자(solution modifier)는 algebra가 정의하는 순서대로 적용된다(SPARQL
1.1 §18.2.5). 그 순서는 `ORDER BY`, 투영, `DISTINCT`, `OFFSET`, `LIMIT`이다.
이들은 모두 SQL 안에서 처리한다.

`ORDER BY`는 변수와 `FILTER`가 지원하는 식을 받는다. 각 정렬
기준(comparator)은 `ASC`(기본값) 또는 `DESC`다. 해는 SPARQL의 순서(§15.1)에
따라 앞에서부터 다음 순으로 정렬된다.

1. 값 없음(바인딩되지 않은 변수, 또는 오류인 식)
2. 빈 노드
3. IRI, 코드 포인트 순
4. 리터럴. `<` 연산자로 두 리터럴의 순서를 정할 수 있으면 `FILTER`와
   마찬가지로 `<`로 정렬한다. 숫자는 XPath 타입 승격을 적용해 값으로,
   문자열은 코드 포인트 순으로 정렬하고, `false`는 `true`보다 앞에 두며,
   dateTime은 시점 순으로 정렬한다.

SPARQL이 순서를 정하지 않은 경우에는 엔진이 정한 고정 순서를 사용한다. 이
순서는 Discussion #63에서 결정했다.

- 종류가 다른 리터럴은 숫자, boolean, dateTime, 문자열, 언어 태그가 있는
  리터럴, 그 밖의 데이터타입 순으로 정렬한다.
- 언어 태그가 있는 리터럴은 문자열 표기로 정렬한 뒤 언어 태그로 정렬한다.
- 그 밖의 데이터타입의 리터럴은 데이터타입 IRI 순으로 정렬한다. 그다음
  `date`와 `time` 컬럼은 값으로, 나머지는 문자열 표기로 정렬한다.
- NaN은 모든 숫자 뒤에 둔다. `numeric`의 NaN과 무한대는 PostgreSQL이 정하는
  위치에 둔다. 데이터타입이 다른 같은 수(`1`과 `1.0`)의 순서는 정해져 있지
  않다.
- `date`와 `timestamp` 컬럼의 무한대 값은 일반 리터럴(`"infinity"`)이며
  문자열 사이에서 정렬된다.

`DESC`는 이 순서 전체를 뒤집으므로 바인딩되지 않은 값이 마지막에 온다.

각 정렬 기준은 SQL 정렬 키 몇 개(term의 종류, 그다음 종류별 값)로 변환된다.
이 키를 사용하므로 SQL 타입이 다른 값과 서로 다른 `UNION` branch의 값도 함께
정렬된다.

단순 `SELECT` 하나가 정렬 기준의 컬럼을 읽고 그 컬럼에 다른 값이 들어갈 수
없으면(필수인 숫자, boolean, dateTime 컬럼), SQL은 컬럼 자체로 정렬한다.
그러면 그 컬럼의 인덱스가 행을 정렬된 순서로 전달한다. 문자열과 IRI는
`COLLATE "C"`로 정렬하므로 다른 collation의 인덱스는 사용할 수 없다.

정렬 키는 추가 컬럼으로 선택되며 결과에는 포함되지 않는다. SQL은 하위 쿼리를
거치면서 순서를 유지하지 않으므로, 행이 도착하는 순서는 가장 바깥 쿼리가
결정한다. 따라서 엔진이 다른 쿼리를 감싸는 모든 쿼리(행 수 세기, 컬럼의
텍스트 캐스트)는 이 정렬 키로 다시 정렬한다.

`v12n explain`에는 컬럼 타입 정보가 없다. 이 명령은 모든 컬럼을 문자열로
정렬하는 형태로 보여 준다.

`LIMIT`과 `OFFSET`은 SQL의 바인드 파라미터다. 쿼리의 `LIMIT`이 행 제한
이하이면 해는 최대 그 수만큼만 남으므로, 결과가 잘렸다고 보고되지 않는다.
쿼리의 `LIMIT`이 행 제한보다 크면 행 제한이 그대로 적용된다.

다음은 미지원으로 거부한다.

- `SELECT DISTINCT`가 투영하지 않는 변수에 대한 `ORDER BY`. 투영된 해 하나가
  `ORDER BY`에서 서로 다른 위치에 놓이는 여러 해를 대표할 수 있다.
- 시간대가 있는 값과 없는 값에 대한 정렬 기준
- `real` 컬럼에 대한 정렬 기준
- 인코딩이 UTF-8이 아닌 데이터베이스의 문자열에 대한 정렬 기준
- `FILTER`와 마찬가지로 그 밖의 함수, 산술, SQL이 계산할 수 없는 문자열 형태
